# 4-Tenant KVM2 Deploy Checklist

What has to be true on the real Hostinger KVM2 box (2 vCPU / 8GB / 100GB NVMe)
before real operations start, across all 4 tenants sharing it.

**This is a companion to, not a replacement for, [GO_LIVE.md](GO_LIVE.md) and
[DEPLOY.md](DEPLOY.md).** Those two were written for a single-tenant
Railway/Vercel + Atlas deployment (one `api`/`web` pair, one `docker compose`
project, `make logs`/`make backup` acting on a single stack). The actual
target here is 4 independent tenant stacks provisioned through
`platform/control-plane`, sharing one Caddy instance and one `mongod` replica
set — every command and smoke-test step in those two docs still applies, but
it has to be run **once per tenant**, not once. Where this doc references a
step from either file, it's calling out the multi-tenant adjustment, not
duplicating the whole step.

**Prerequisites — do these first, in order:**
1. Part 1 (dashboard-counter fix — see `server/server.js`'s `TenantStats`/
   `ProductStats`, and `applyStatsDelta` in `server/features/orders.js`) is
   deployed to the image these tenants will run.
2. Part 2's load test (`scripts/k6/`) has been run against a rehearsal
   provisioning of all 4 stacks, capped at the real box's resource limits,
   and met the thresholds in `scripts/k6/README.md`.
3. Part 3's findings (`SECURITY_REVIEW.md`) — the 5 fixed findings are in the
   image; the "verify at deploy" section of that doc is what §2 below covers.

---

## 1. Provisioning

- [ ] All 4 tenant stacks created through `platform/control-plane`
  (`POST /api/tenants` — the control plane's own provisioning flow, the same
  mechanism Part 2's load test validated). Not a manual `docker compose up`
  per tenant — that's not the path that will be used going forward, so it's
  not the path worth testing.
- [ ] Caddy routes all 4 subdomains correctly (`platform/tenants-caddy/*.caddy`,
  generated by the control plane on create). Confirm there's no fallback vhost
  that could serve one tenant's app under another tenant's subdomain — this is
  the actual enforcement mechanism behind the cross-tenant isolation note in
  `SECURITY_REVIEW.md` (app-level `tenantScope` is a documented no-op; Caddy +
  per-tenant JWT_SECRET + separate database are what actually isolate tenants).
- [ ] Each tenant has its own generated `JWT_SECRET` in
  `platform/tenants/<slug>/.env` — confirm none are default, empty, or shared
  across tenants (`grep JWT_SECRET platform/tenants/*/.env | sort | uniq -c`
  on the `JWT_SECRET=` value — every count should be 1).
- [ ] Per-tenant cgroup limits (`MEM_LIMIT`/`CPU_SHARES` in each tenant's
  `.env`, set via `PATCH /api/tenants/:slug/resources`) are deliberate, not
  left at the `platform/tenant-compose.yml` defaults (1024MB/1024 shares).
  With 8GB total shared across 4 app+web pairs plus `mongod`
  (`--wiredTigerCacheSizeGB 2` per `platform/docker-compose.yml`), Caddy, and
  the control plane, budget roughly 1–1.5GB per tenant and leave headroom.
- [ ] The shared `mongod` is confirmed running as a healthy `rs0` replica set
  (`docker exec semivra-platform-mongo-1 mongosh --eval 'rs.status().ok'`)
  with 4 separate logical databases, one per tenant (`semivra_<slug>`, per the
  control plane's own wipe-route naming). A standalone `mongod` here silently
  breaks every transactional order-completion path in the app — this is not
  optional.

## 2. Hardening & secrets

- [ ] Each tenant's boot-time checks pass: no weak `JWT_SECRET`, no default
  `ADMIN_PASS`, `ALLOWED_ORIGINS` set correctly to that tenant's own subdomain
  (check `server/server.js`'s fail-fast boot block — a tenant that boots with
  a weak config should refuse to start, not warn and continue).
- [ ] Control-plane port 9000 confirmed bound to `127.0.0.1` only and blocked
  externally at the firewall. This is already correct in
  `platform/docker-compose.yml` (`ports: ["127.0.0.1:9000:9000"]`) — verify
  the real box's `ufw`/`iptables` rules don't additionally publish it, and
  that nothing overrides the compose file's port mapping on this specific
  deploy. If this is ever wrong, `SECURITY_REVIEW.md` finding #4 (control-plane
  rate limiting) becomes the only thing standing between the internet and a
  root-equivalent Docker socket — treat any external reachability here as a
  stop-ship, not a warning.
- [ ] `CP_PASSWORD` / `CP_DANGER_PASSWORD` are strong, unique, and different
  from each other (the control plane refuses to boot otherwise, but confirm
  they weren't set to the same low-entropy value that happens to differ by one
  character).
- [ ] TLS/HSTS active on all 4 subdomains via Caddy (`curl -I
  https://<tenant>.<domain>` for each — expect `Strict-Transport-Security`).

## 3. Backups, monitoring, rollback

- [ ] `scripts/backup-mongo.sh` scheduled (cron, per DEPLOY.md §"Schedule
  daily backups") covering **all 4 tenant databases** — confirm the script
  actually iterates `semivra_<slug>` for each tenant, not just the default
  single-tenant DB name it was originally written for.
- [ ] Restore path tested **at least once** before go-live — pick one
  tenant's backup, restore to a scratch database, verify document counts, per
  DEPLOY.md's Week-1 Verification §5, but done pre-launch here instead of
  during week 1.
- [ ] Disk usage monitored on the 100GB NVMe — 4 tenants' growing Mongo data
  plus backups will compound faster than a single-tenant deploy. Set an
  actual alert threshold (e.g. 80% via your uptime-monitor's disk check, or a
  cron that mails past a threshold), not just a periodic manual `df -h`.
- [ ] Per-tenant logs accessible: `GET /api/tenants/:slug/logs` (control
  plane) — confirmed working for each of the 4 slugs, not just the one used
  during development. `Makefile`'s `logs`/`logs-api` targets assume a single
  `docker compose` project and do **not** work as-is against this control
  plane setup; use the control-plane endpoint or `docker compose -p <slug> -f
  platform/tenant-compose.yml logs` instead.
- [ ] Confirm a single tenant's stack can be restarted or rolled back
  independently without affecting the other 3: exercise
  `POST /api/tenants/:slug/restart` (well, `start`/`stop`/`rebuild` — see
  `platform/control-plane/server.js`) against one tenant while the other 3
  are under light synthetic load (reuse `scripts/k6/01-single-tenant-baseline.js`
  against the other 3), and confirm they're unaffected. Containers are
  isolated in principle — this step is what actually verifies it against this
  control plane's real behavior instead of assuming it from the architecture.
- [ ] `SENTRY_DSN` (optional, per DEPLOY.md's env reference) set per tenant if
  you want error monitoring — or rely on the control plane's own
  `GET /api/errors` cross-tenant error aggregation, which reads each tenant's
  capped `errorevents` collection directly and needs no per-tenant Sentry
  project.

## 3b. Updating all apps after go-live

Deploying a new version of the app to every tenant is a one-click action in
the control plane — **"Update all apps"** (top-right of the panel). It runs in
two phases so the outage is as short as possible:

1. **Downloading update & building** (no downtime): if `STACK_ROOT` is a git
   checkout, it `git pull --ff-only`s the latest code; otherwise it builds from
   whatever is on disk. Then it builds the **one shared `semivra-api:shared`
   image** (the API takes no build args — it's the same image for every tenant,
   so it's built once, not per-tenant) and each tenant's own `web` image.
   Running apps are untouched during this phase.
2. **Applying update** (~1 min, apps briefly restart): each tenant's containers
   are recreated onto the freshly-built images, in sequence. This is the only
   window where the apps are momentarily unavailable.

If the build phase fails (e.g. a bad `git pull`, or a compile error), **nothing
is applied** — the running apps keep serving the old version until you fix it
and retry. The modal reports per-tenant health at the end.

Backing routes (control plane, SSH-tunnel only): `POST /api/update/prepare`,
`POST /api/update/apply`. A single tenant can still be updated in isolation via
the per-tenant **Rebuild** button (`POST /api/tenants/:slug/rebuild`).

> **Shared vs. per-tenant images:** `semivra-api:shared` is one image all
> tenants run (config is 100% runtime env). `semivra-web:<slug>` stays
> per-tenant because it bakes each tenant's business name/theme/billing in at
> build time. A server-only change therefore rebuilds one image + restarts
> everyone; a branding change to one tenant only rebuilds that tenant's web.

## 4. Sign-off

- [ ] Every item above checked for **all 4 tenants**, not just the first one
  provisioned — the first tenant tends to get the most manual attention during
  setup; the 4th is where copy-paste config mistakes (wrong `JWT_SECRET`,
  wrong `ALLOWED_ORIGINS`) actually surface.
- [ ] `SECURITY_REVIEW.md`'s "Follow-ups requiring a deployed target" section
  is run against the real box: OWASP ZAP baseline scan, live control-plane
  external-reachability check from outside the SSH tunnel, and confirmation
  that the `npm audit` CI gate is actually blocking on both `client` and
  `server` (check an actual recent `.github/workflows/ci.yml` run, not just
  that the step exists in the workflow file).
- [ ] Run GO_LIVE.md §2's staging verification checklist and DEPLOY.md §"Day-1
  Deployment"/7's smoke test against **each** of the 4 tenants post-provision
  — same steps, four times, not assumed to pass everywhere because it passed
  once.
- [ ] Update `GO_LIVE.md` and `DEPLOY.md` themselves with whatever this round
  surfaced that's durably true going forward (e.g. if `Makefile`'s `logs`
  target gets a tenant-aware variant, document it there — this checklist is a
  one-time pre-launch pass, those two are the living runbooks operators will
  actually reach for afterward).
